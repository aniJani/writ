# SEP-2848 conformance mapping

This page maps Writ's conformance corpus to the conformance statements of SEP-2848, says which of the SEP's requirements the kernel decides, and lists what a server built on Writ still owes. `corpus/sep-2848.json` holds the same mapping as data, and `WritTests/Sep2848.lean` checks it during `lake build`.

## What SEP-2848 is

SEP-2848, "Asynchronous Approval for Tool Calls", is an MCP extension proposal: an MCP server gates a `tools/call` on an approval decided out of band (by a human, an agent, a policy engine or a ticketing system), and the client sees only a SEP-2663 task. The approval protocol itself never crosses the MCP wire.

Status as of 2026-10-20: a draft in the open pull request [modelcontextprotocol/modelcontextprotocol#2848](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2848), with no sponsor ("None (seeking sponsor)"). The text cited here is `seps/2848-asynchronous-approval-for-tool-calls.md` at the pull request's head commit `e7fff475323f5f6f930396d7a43df06115fe1e6f` on `mcguinness/modelcontextprotocol`. Its last activity was a review on 2026-10-20. The SEP may still change; this page follows that commit.

The SEP defines no conformance scenarios. Its Reference Implementation section requires a scenario and a `sep-NNNN.yaml` traceability file before Final and lists seven MCP-observable statements a scenario must cover. Those seven statements are the rows below.

## Who decides what

The SEP's server owns the MCP wire: `CreateTaskResult`, `tasks/get`, `tasks/update` and `tasks/cancel`, task retention and `ttlMs`, the backend submission with its idempotency key, callbacks, and the content and `_meta` of the final `CallToolResult`. Writ owns the decision at three points: at the call (`propose`, whose `needs_approval` is the SEP's requestable denial), at the approval (`approve`, `reject`, `approval_expire`, `cancel`), and at execution (`dispatch`, whose `dispatch_claimed` is the SEP's execution claim). The server feeds those events to the kernel, stores the state with compare-and-swap on `state_version`, and runs the tool only on `dispatch_claimed`.

The server folds the SEP's immutable call binding into Writ's `call_digest`: the tool, the full arguments and the subject or resource, hashed (for example with the `writ-call-v1` digest of `@anijani/writ`). The originating principal is the session's requester, and every approval names the session in its `request_id`, so a server runs one session per originating principal.

## The seven statements

Each kernel-decidable statement has one trace in `corpus/examples/mcp-approval.jsonl` and is witnessed by other corpus traces too. The theorems are those of the [Proof status](../README.md#proof-status) table, explained in `docs/theorems.md`; each is pinned in `WritProofs/Axioms.lean`.

| # | Statement | Writ | Traces | Theorems |
|---|---|---|---|---|
| 1 | requestable denial returns a task without executing | kernel: `propose` answers `needs_approval`; a dispatch before approval is refused `call_awaiting`, and nothing claims a call with consent until its approvals meet that consent | `mcp-approval/s1-pending-not-executed`, `web-chat/parallel-calls`, `web-chat/reload-repeat` | `consent_claim`, `consent_claim_fired`, `dispatch_claimed_iff` |
| 2 | approval resumes execution at most once | kernel: one claim per call; a second dispatch is refused `call_dispatched`, and one after the result `call_ended` | `mcp-approval/s2-approved-once`, `langgraph-resume/approval-hours-later`, `web-chat/reload-repeat`, `device-split/device-never-reports` | `at_most_once`, `retry_after_unknown`, `profile_unknown_final` |
| 3 | terminal denial is a `completed` task whose body marks `denied-not-executed`, distinct from an execution error | kernel: a rejected, expired or cancelled call never claims, and a `result` or `outcome_unknown` is accepted only for a call whose status is `dispatched`, so `failed` and `unknown` follow that status. That a call reaches `dispatched` only through a claim is a property of the kernel, not separately proved. The profile maps the call status to the disposition (below) | `mcp-approval/s3-denied-not-executed`, `web-chat/reject-then-retry`, `device-split/device-never-reports` | `terminal_absorbing`, `no_reject_before_claim`, `rejected_claim`, `accepted_iff_reject`, `accepted_iff_result`, `accepted_iff_outcomeUnknown` |
| 4 | a changed envelope (tool, arguments, principal, subject/resource) requires new approval | kernel: approvals bind the digest they reviewed and the current generation; a dispatch with another digest is refused `digest_mismatch`, a re-proposal of the call with another tool or digest `duplicate_call`, and an approver's edit starts a new generation, which only approvals of that generation (the edit counts as one) can authorize | `mcp-approval/s4-changed-arguments`, `langgraph-resume/edit-restarts-tally`, `langgraph-resume/resumed-repeat-edited-digest`, `langgraph-resume/argument-swap` | `consent_claim`, `approve_fresh`, `call_origin`, `requester_origin` |
| 5 | a cancelled or expired task cannot later execute | kernel: `cancel`, `approval_expire`, the approval TTL and the authorized TTL; cancelled and expired calls are terminal and never claim | `mcp-approval/s5-cancelled-or-expired`, `langgraph-resume/approval-hours-later`, `coding-agent/kill-stops-everything` | `terminal_absorbing`, `accepted_iff_cancel`, `approve_fresh_event`, `claim_authorized_ttl_event`, `kill` |
| 6 | result retrieval does not expose backend artifacts | host only: Writ's verdicts and state carry no backend material | excluded | excluded |
| 7 | submission input flows through the task input channel | host only: submission input travels in `tasks/update` or an MRTR retry, which the kernel never sees | excluded | excluded |

The five `mcp-approval` traces share one policy: an MCP server whose `payments.refund` needs `per_call` consent with an approval TTL of one hour (`approval_ttl_ms` 3600000) and an authorized TTL of ten minutes (`authorized_ttl_ms` 600000), and whose `docs.read` needs none. In `s4-changed-arguments` the approver's edit authorizes the new generation at once, because under `per_call` consent an edit counts as the editor's approval of the digest it set; `langgraph-resume/edit-restarts-tally` shows the same edit under a quorum of two, where it voids the other approval and asks again.

## Disposition mapping

A completed SEP-2848 task carries `io.modelcontextprotocol/tool-approval-disposition`. The `mcp-tool-approval` profile derives it from the call's status (`docs/formats.md`, MCP SEP-2848 profile), in Lean, in `writ explain --profile` and through `kernel.profile` in `@anijani/writ` and in the Python package `writ-kernel`, so a server does not keep its own table:

| Call status | Disposition |
|---|---|
| `succeeded` | `approved-executed` |
| `rejected`, `expired`, `denied`, `denied_at_dispatch`, `declined` | `denied-not-executed` |
| `failed` | `execution-error` |
| `unknown` | `outcome-unknown` |
| `cancelled` | `cancelled`, the SEP-2663 task status; SEP-2848 gives a cancelled task no disposition |

Notes:

- `awaiting` and `authorized` are not terminal: the task stays `working`. `dispatched` is claimed but not yet reported: the task stays `working` until a `result` or `outcome_unknown`.
- A `propose` answered `denied` is a non-requestable denial, which the SEP answers without a task; the row matters only for a call that already has one.
- `failed` needs status `dispatched` first (`accepted_iff_result`), which the kernel reaches only through a claim, so it is never the SEP's task status `failed`, which R27 allows only before a claim.
- `declined` comes after a claim, and a host reports it only when the tool had no effect (`docs/design.md`, section 6), so `denied-not-executed` is accurate; a host that cannot tell reports the outcome it observed instead.
- A task the client cancelled with `tasks/cancel` ends in SEP-2663's `cancelled` status; the call never claimed (R55).
- The profile also gives the SEP-2643 envelope of each verdict (`remediation: available` with a `task` hint for `needs_approval`, `unavailable` with the reason code, retry class and model message for a denial) and `writ check --profile mcp-tool-approval` reports `retry_after_unknown` as an error (R47). The policy above passes it (`tests/cli/profile-check-corpus-mcp-approval.case`): the profile does not ask for `binding: immutable`, because SEP-2848's immutable call binding is the approval's binding to the call digest, which holds under either setting, and an approver's edit is a changed envelope that needs new approval (statement 4).

## Requirements the kernel decides

The R numbers are Writ's own numbering of the SEP's normative sentences (every sentence with an RFC 2119 keyword in capitals, in order) at the head commit above; the SEP does not number them. Each quote is verbatim.

| R | Requirement | Writ |
|---|---|---|
| R14 | "**At-most-once and deduplication.** The server controls both task creation and execution, so it MUST execute the approved tool at most once per task." | One claim per call (with `retry_after_unknown` off; with it on, at most `max_attempts` claims, each after an Unknown): `at_most_once`. A second dispatch is refused `call_dispatched`, one after the result `call_ended` (`mcp-approval/s2-approved-once`). |
| R16 | "Once a task reaches a terminal disposition it is final, permanently fenced against execution, and MUST NOT be reopened." | Terminal statuses never change (`terminal_absorbing`, `calls_keep`); an approval, dispatch, result or cancel of a call that ended is refused `call_ended`, and a repeated propose answers `existing` with the status. On an `unknown` call a result or cancel is refused `call_unknown` and a dispatch `retry_not_allowed`, and `reconcile` is accepted, recording evidence without changing its status. The one exception, the retry edge from `unknown`, needs `retry_after_unknown`, which a server leaves off under SEP-2848 (R47). |
| R23 | "The server MUST check the immutable call binding before executing, and MAY record the policy id and version for audit and drift detection (recorded, not pinned)." | A dispatch carries the `call_digest` and is claimed only if it equals the call's digest; otherwise it is refused `digest_mismatch` (`dispatch_claimed_iff`, `consent_claim`). |
| R24 | "An MRTR retry that resumes the original call, echoing it with `requestState`, MUST match the immutable call binding: the server MUST reject it if the tool, arguments, or originating caller differ." | A repeat of the call id with another tool or digest is refused `duplicate_call`, a dispatch with another digest `digest_mismatch`, and an approval whose `request_id` names another session `stale_request` (`call_origin`, `requester_origin`, `mcp-approval/s4-changed-arguments`). |
| R27 | "A task MUST enter `failed` only before an execution claim (see Completion); any failure after the claim MUST be a `completed` `CallToolResult` with `execution-error` or `outcome-unknown`, so a possible side effect is never hidden behind a retryable `failed`." | A `result` or `outcome_unknown` is accepted only for a call whose status is `dispatched` (`accepted_iff_result`, `accepted_iff_outcomeUnknown`), and the kernel reaches `dispatched` only through a claim (not separately proved), so `failed` and `unknown` come after a claim; a call that ends before the claim is `rejected`, `expired`, `cancelled` or `denied_at_dispatch`. |
| R33 | "A client that does not recognize a disposition value MUST treat the operation as possibly executed and MUST NOT retry it automatically." | R33 binds the client; Writ supplies the matching guarantee on the server: an `unknown` call is possibly executed and is never dispatched again without `retry_after_unknown` (`at_most_once`); a late report is accepted only as `reconcile` (`device-split/device-never-reports`). |
| R37 | "Ordering it this way closes the window where a stale callback could still act: a callback or poll result for a consumed generation MUST NOT cause re-evaluation or execution, even when it is authentic, since the decision has moved on." | An `approve` or `approval_expire` must echo the current request id, generation included (`approve_fresh`, `accepted_iff_approvalExpire`), and an older one is refused `stale_request`; an approval of a call that ended is refused `call_ended` (`langgraph-resume/edit-restarts-tally`). A `reject` may name an older generation of the same call (`accepted_iff_reject`), but it can only end the call, never run it. |
| R44 | "A task that proceeds to execution MUST make a single atomic compare-and-set from pre-execution to execution-claimed; this happens at most once and is mutually exclusive with cancellation and expiry (a task that is denied, cancelled, or expired makes no claim)." | `dispatch_claimed` is the claim, and the state is stored with compare-and-swap on `state_version`. At most one claim per call (`at_most_once`); `cancel` is accepted only for a call whose status is `awaiting` or `authorized` (`accepted_iff_cancel`) and `approval_expire` only for an `awaiting` one (`accepted_iff_approvalExpire`); both leave a terminal status that never claims (`terminal_absorbing`). That a call reaches `dispatched` only through a claim is a property of the kernel, not separately proved. |
| R45 | "The claim is the irrevocable authorization-enforcement point: all validity checks, the identity and freshness checks above and the approval expiry, MUST hold at the moment of the claim, and a cancellation or expiry that precedes the claim wins (the exact cancellation boundary, see Cancellation)." | A dispatch re-evaluates at the claim (`dispatch_claimed_iff`): permission (`permission_claim`), guards, meters (`no_claim_over_cap`), escalation (`blocked_claim`), the rejection memory (`rejected_claim`), kill (`no_claim_killed`) and the authorized TTL (`claim_authorized_ttl_event`); a dispatch after that TTL is `dispatch_denied` with `authorization_expired`. A cancel or expiry before the dispatch leaves the call terminal, and the dispatch is refused `call_ended` (`mcp-approval/s5-cancelled-or-expired`). |
| R46 | "Once the claim succeeds the server invokes the tool at most once and MUST carry it through even if the approval expiry elapses during invocation, since authorization was enforced at the claim." | A `result` for a dispatched call is accepted whatever its time (`accepted_iff_result`), so a call claimed in time is carried through after its TTL. |
| R47 | "If it cannot determine whether invocation or the side effect completed (a crash after the claim, before or after invoking), it MUST NOT re-invoke, and the task completes `outcome-unknown`." | `outcome_unknown` makes the call `unknown`, which maps to `outcome-unknown`; without `retry_after_unknown` it is never dispatched again (`at_most_once`, `retry_after_unknown`, `device-split/device-never-reports`), and under a policy that passes `writ check --profile mcp-tool-approval` no dispatch of it is accepted (`profile_unknown_final`). |
| R55 | "The server MUST NOT both execute the tool and report `cancelled`." | `cancel` is accepted only for an awaiting or authorized call (`accepted_iff_cancel`), and a cancelled call never claims (`terminal_absorbing`). |
| R62 | "**Confused deputy.** An approval applies only within the originally evaluated scope; the server MUST NOT let a client steer execution to a different operation." | An approval counts only for the digest it reviewed (or, for an edit, the digest it set) and the generation it echoed (`consent_claim`, `approve_fresh`); the claim dispatches that digest. The client cannot change a call's tool or digest (`duplicate_call`, `digest_mismatch`), and `binding: immutable` also forbids approver edits (`mcp-approval/s4-changed-arguments`). |
| R65 | "**Expiry.** Before an execution claim, after expiry the server MUST stop honoring the approval and durably fence the task against a late approval or callback; the claim is the enforcement point, so an approval valid at the claim carries through (see Completion)." | An `approve` after the approval TTL is refused `approval_expired` (`approve_fresh_event`), and `approval_expire` makes the call `expired`, terminal and fenced (`terminal_absorbing`). The claim checks the authorized TTL (`claim_authorized_ttl_event`), and a claimed call carries through (R46) (`mcp-approval/s5-cancelled-or-expired`, `langgraph-resume/approval-hours-later`). |

## What a server built on Writ still owes

The kernel decides when a call may run; it does not speak MCP, store tasks or talk to the backend. A server built on Writ still owes R9 (no backend binding material on the wire), R10 to R13 (submission intent, idempotency key, durable handle, reconciliation on restart), R17 to R19 (`ttlMs` and retention), R21 and R22 (model-facing text), R31 and R48 to R51 (the disposition, the body and the envelope agreeing), R54 (no `notifications/cancelled` for tasks), R61 (task access control), R63 and R64 (callback authenticity), and R67 to R69 (rate limits and protecting stored records). It also chooses the `call_digest` (above), writes the profile's dispositions and envelopes into its results, and leaves `retry_after_unknown` off for every action behind SEP-2848, since R47 forbids re-invoking a call whose outcome is unknown (`writ check --profile mcp-tool-approval` reports it).

## Relation to a SEP-2484 traceability file

SEP-2484 asks each Standards Track SEP to ship a conformance scenario and a `sep-NNNN.yaml` traceability file with one row per MUST, MUST NOT, SHOULD and SHOULD NOT, each row naming a check or giving an exclusion reason. `corpus/sep-2848.json` has the same shape for the SEP's seven statements: `sep`, `spec_url`, and one row per statement with either the Writ traces and theorems that cover it (where the conformance repository would name its checks) or an `excluded` reason. When SEP-2848 gets a scenario, each kernel row becomes a `check:` row whose check drives the trace's events through the server, and the table above gives the per-requirement rows for the requirements the kernel decides. `WritTests/Sep2848.lean` fails the build unless statements 1 to 7 each appear exactly once, each has traces and theorems or an exclusion but not both, every trace id is a corpus trace and every theorem is pinned in `WritProofs/Axioms.lean`.

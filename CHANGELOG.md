# Changelog

Writ follows semantic versioning. Any change to the trace or policy JSON schema is listed here under its own heading, because conformance runners in other languages depend on it.

## Unreleased

Layer 2 of the policy format (labels, rules and `extends`), expanded to the layer-1 policy the kernel runs, with spec section 8's theorem 13 proved over the expansion, and the four presets from the spec. The `writ-tool-v1` tool digest and the per-action `source` field that records it; `writ import mcp`, which drafts a layer-2 policy from an MCP tool list; `writ check --tools`, which detects changed tool definitions; `writ diff`, which lists the verdicts a policy change alters in recorded traffic; and `writ traces`, which generates conformance traces from a policy. The standard corpus generated from nine fixture policies, pinned by a manifest and packed into the release tarball by `scripts/corpus.sh --tar`; hand-written attack traces; and `writ-fuzz --judge`, which checks every corpus trace against the spec-side checkers. The kernel, `Writ.Api`, the WebAssembly build and `@anijani/writ` still accept only layer 1; their only changes are the wording of three grant messages, accepting `source`, `toolDigest` in `@anijani/writ`, and the MCP SEP-2848 profile, which `Writ.Api`, the WebAssembly build and `@anijani/writ` gain as one additive function. Beside them, `writ-kernel`, the Python binding, on a standalone link of the same WebAssembly kernel; and the release workflow with a local rehearsal, which builds and checks every release asset but has not yet run on GitHub, so nothing from this section is published. No format version changes: the new policy fields are additive and optional, so the next release takes a minor bump.

### Added
- `writ expand <policy.json> [--out <file>]` prints the layer-1 policy a layer-2 policy expands to, as canonical JSON on one line with each action's `review` and `messages` copied from the files that write them, so its digest is stable. It runs the same check as `writ check` and, when that reports errors (layer-2 problems or errors of the expanded policy), prints them instead, writes nothing and exits 1; warnings do not stop it.
- `writ check` checks a layer-2 document: its `extends` and layer-2 problems, then the expanded policy's errors and warnings, with the usual exit codes. With `--json`, `policy_digest` is the digest of the `writ expand` output. A layer-1 document is checked exactly as before. A policy that extends another may not set the policy-level `mode` to `log_only` (`extends_log_only`), and an extended file's labels and rules are checked against the dimensions it and the files it extends declare, not the extending policy's, so an extending policy cannot reorder a dimension a parent uses without declaring it.
- Both commands resolve `extends` against the directory of the file that lists it, depth-first in `extends` order, reading each file once by its real path (a diamond works and reports problems once, and symbolic links cannot multiply files), at most 8 files deep and 256 files in all. A cycle, an unreadable file, a deeper chain and a 257th file are errors that name the chain (`extends_cycle`, `extends_unreadable`, `extends_too_deep`, `extends_too_many`), exit 1. An empty `extends` path is a decode error.
- `writ digest` and `writ oracle` refuse a layer-2 document with a message that points at `writ expand`, instead of an `unknown field` error.
- The layer-2 types (`Writ/Author/Layer2.lean`), the strictness order and join of every requirement field (`Writ/Author/Join.lean`), `expand` and the layer-2 check `Policy2.check` with its problem codes (`Writ/Author/Expand.lean`), and the layer-2 codec (`Writ/Codec/Layer2.lean`).
- Theorem 13 (expansion soundness) in `WritProofs`: `expand_check`, `expand_actions`, `expand_explicit`, `expand_rule`, `expand_rule_resolved`, `expand_rule_checked`, `expand_mono`, `expand_mono_resolved`, `expand_mono_checked`, `expand_parent` and `expand_parent_checked` in `WritProofs/Expand.lean`, and the lattice laws of every field's join in `WritProofs/Join.lean`, pinned in `WritProofs/Axioms.lean` and described in `docs/theorems.md`.
- The four presets from the spec ship as layer-2 files in `schema/presets/`: `generic-tiers` (`risk` from `read` to `destructive`), `mcp-annotations` (the MCP tool annotations, an unannotated tool taking MCP's pessimistic defaults), `mcp-risk-metadata` (SEP-2793 risk metadata, `approval_recommendation: multi` mapping to quorum 2) and `axes` (effect, reversibility, audience, value, data). Each has only `labels` and `rules`; a policy uses one by listing its relative path in `extends`. `mcp-risk-metadata` and `axes` share the `reversibility` dimension with the same order and rule, so a policy can extend both. `schema/presets/README.md` lists every dimension and rule, and `tests/cli/presets/` has a sample policy for each, expanded and checked by `scripts/cli-test.sh`.
- `docs/formats.md` describes layer 2: its fields, how `extends` is resolved, how an action expands, `writ expand` and the layer-2 errors. The layer-2 example in section 5 of `docs/design.md` gains `writ` and `approver_roles` and is now a tested file (`tests/cli/layer2/spec-example.json`). `scripts/cli-test.sh` also checks that every policy `writ expand` prints in its cases passes `writ check`.
- The `writ-tool-v1` tool digest: `"sha256:"` plus the SHA-256 of the RFC 8785 canonical JSON of `{"t": "writ.tool.v1", "tool": <tool>}`, every member of the MCP tool definition included. Tool definitions may hold fractions, so a standalone canonicalizer (`Writ/Json/Jcs.lean`) keeps numbers as text: a literal with at most 15 significant digits and a magnitude of 0 or within 1e-300 to 1e300 prints as ECMAScript prints it, and any other number is refused with its JSON path. `Writ/Codec/Tool.lean` reads a tools.json document (an MCP `tools/list` result or a bare array, a `nextCursor` of null accepted like an absent one, its other members ignored) and digests each tool. `@anijani/writ` exports `toolDigest` and `toolPreimage`. `corpus/digests/tool-v1.jsonl` holds the test vectors, run by the Lean tests and the package tests.
- An optional per-action `source` field, `{ tool_digest, server?, tool?, annotations? }`, records the MCP tool an action was written for. The kernel accepts and ignores it, as it does `review`. In layer 2 every file that writes it for an action must agree (`conflicting_field`), and `writ expand` copies it into its output with `review` and `messages`.
- `writ import mcp <tools.json> [--server s] [--preset-dir d] [--out f]` drafts a layer-2 policy from an MCP `tools/list` result or an array of tools: one action per tool, extending `mcp-annotations` (and `mcp-risk-metadata` when a tool carries a SEP-2793 field), with `approver_roles: ["owner"]` as a placeholder. Annotations are untrusted server claims and every MCP default is the pessimistic value, so import never lowers a label: every action is labeled at each dimension's strictest value, the server's annotations are copied into `source.annotations` with the tool digest in `source.tool_digest`, and stderr names each claim not applied. `writ expand` of a draft therefore requires consent for every tool and allows no grant. An annotation member a policy cannot hold (a fraction or an integer beyond plus or minus (2^53 - 1)) is left out with a line on stderr, so the draft always parses. Exit 2 for a usage or input error, including no tools, a duplicate tool name and a number the tool digest refuses.
- `writ check <policy.json> --tools <tools.json> [--server s]` compares each action's `source.tool_digest` with the `writ-tool-v1` digest of the tool it names (`source.tool`, else the action name) in a server's current tool list, read exactly as `writ import mcp` reads it. A changed tool (a rewritten description, schema or annotation under the same name) is the error `tool_changed`, naming the action and both digests; a tool missing from the list is the warning `tool_missing`; a listed tool that no compared `source` pins is the warning `tool_unpinned` when some action still allows it (named after the tool or naming it in `source.tool`, without a `source` or, under `--server`, with one for another server, or named after the tool while its `source.tool` names another), so later changes to it go undetected, and `tool_unlisted` when no action names it, so default deny refuses it. Key order, whitespace and number spelling never count as a change. `--server` compares only the actions whose `source.server` is that name, and is at most 512 UTF-8 bytes. A layer-2 policy is compared after expansion, so a `source` in a file it extends counts. The findings appear in text and `--json` with the usual exit codes.
- `writ diff <old.json> <new.json> <events.jsonl> [--json]` replays recorded events under two policies, each layer 1 or 2 (expanded as `writ expand` expands it), and lists the events whose verdict changed, `state_version` aside: one line per changed event with both verdicts, the first marked `(first divergence)`, then a count, or with `--json` one object per changed event. Each run starts from a fresh state under its own policy digest, and diff sets each event's `state_version`, and a `session_start`'s `policy_digest`, to that run's, so traffic recorded under the old policy starts under the new one (a `session_start` may omit `policy_digest`) and one changed verdict does not turn every later event into `state_version_mismatch`. The count notes the events both policies rejected. An events file holds one session: events carry no session id, so a file whose first event is not a `session_start`, or that holds a second one, is refused, naming the line. Exit 0 when nothing changed, 1 when something did, 2 for a usage, IO or policy error, including an empty or undecodable event line, named by its line number.
- `writ traces <policy.json> [--depth N] [--max-states M] [--out <dir>]` explores a policy's states breadth-first from the initial state over a small alphabet of events (spec section 9) and prints, one `writ.trace/1` trace per line, the shortest trace for every accepted transition between abstract states (states keyed by their canonical JSON without `state_version` and `last_seq`, with call ids, digests and approver principals other than the requester and `agent` renamed by first occurrence; grant ids are kept because the kernel picks grants in id order), then the first rejected event found for each event type and reason. Every event pins the whole verdict. Trace ids are `<name>/a/<k>` and `<name>/r/<event type>/<reason>`. The policy may be layer 1 or 2, and each trace carries the layer-1 policy (for layer 2, exactly what `writ expand` prints). `--depth` (default 4) counts events after `session_start`, `--max-states` (default 20000) stops a run that grows too large and marks it truncated on stderr, and `--out` writes `<dir>/<name>.jsonl`. An action whose name, guard names or escalator names an event cannot hold is left out with a line on stderr, and no event time, expiry or count goes past 2^53 - 1, so every trace replays. The output is the same bytes on every run. `docs/formats.md` (Trace generator) lists the alphabet, the key, the emission rules and sizes by depth. The explorer is `Writ/Explore` (`Explore.run`, `Explore.key`), outside the WebAssembly build. `scripts/cli-test.sh` checks that `writ traces` gives the same bytes on a second run and that its traces replay.
- `writ replay --coverage` adds a last line, `{"reasons":[...],"decisions":[...]}`, listing each reason code and decision in the verdicts the replay gave, sorted: the reasons of rejected events, of `denied` and `dispatch_denied` decisions, of `existing` statuses and of `would_deny`.
- The standard corpus: nine fixture policies in `corpus/standard/fixtures/` (`basic`, `quorum`, `grants`, `meters`, `meters-settle`, `lifecycle`, `shadow`, `retry`, `escalation`), each with at most 4 actions, from which `writ traces` generates 23764 traces (23808 with the 44 hand-written ones). The traces are not committed: `corpus/standard/manifest.json` pins each fixture's depth, `max_states`, trace and state counts, truncation and the SHA-256 of its output, and `corpus/standard/uncovered.json` lists the reason codes nothing reaches (none). `corpus/standard/README.md` says what each fixture covers.
- `scripts/corpus.sh` regenerates the standard corpus into `build/corpus/standard/`, fails with `the generated corpus changed; review the difference, then run scripts/corpus.sh --update` when it differs from the manifest, replays it with `corpus/examples` (and `corpus/attacks` when present), and fails unless every code in `schema/reasons.json` is reached or listed in `uncovered.json` and no listed code is reached. `--update` rewrites the manifest; `--tar` also writes `build/writ-corpus-<version>.tar.gz` with the generated and hand-written corpora, the digest vectors and the READMEs. CI runs it. `docs/formats.md` (Standard corpus) describes the manifest, `uncovered.json` and the script.
- Hand-written attack traces in `corpus/attacks/`: one file per red-team scenario of spec section 9 (cross-session escape, rollback, quorum edit laundering, stale dialog, rejection shopping) and `asu.jsonl` with one trace per attack of the ASU catalogue (arXiv 2610.21063) that the kernel can express; `corpus/attacks/README.md` names the rule that stops each and why the other ASU attacks are outside the kernel. `lake build` replays them (`WritTests/Corpus.lean`) and `scripts/corpus.sh` counts them toward coverage.
- `writ-fuzz --judge <traces.jsonl>...` is a spec-side judge: it runs each trace's events through the kernel, one session from a fresh state per trace, and checks every verdict and state against the checkers in `WritSpec`, which restate the design spec without reading the kernel. It prints one line per violation, then `judged T traces, V violations`, and exits 1 on any violation. `scripts/corpus.sh` judges the generated and hand-written corpora with it (no violations), and its self-test, checked when `writ-fuzz` is built, checks that three inline mutants are flagged and the real kernel is not. `docs/formats.md` (Standard corpus) describes it.
- The MCP SEP-2848 profile `mcp-tool-approval` (`Writ/Profile/McpToolApproval.lean`, outside the kernel): `disposition` maps each terminal call status to its SEP-2848 string (`approved-executed`, `denied-not-executed`, `execution-error`, `outcome-unknown`, and SEP-2663's `cancelled`), and `envelope` maps a verdict to its SEP-2643 structured-denial envelope, following the draft at the commit now pinned as `sep2643_url` in `corpus/sep-2848.json`: `remediation: "available"` with a `task` hint and the request id for `needs_approval`, and `remediation: "unavailable"` with the reason code, its retry class and its reviewed model message, and nothing else, for a `denied` or `dispatch_denied` decision or a rejected verdict. `docs/formats.md` (MCP SEP-2848 profile) describes both and the member names.

### Changed
- The model messages of `duplicate_grant` and `unknown_grant` no longer tell the model to use a new grant id or resend: creating and revoking a grant are approver events the model cannot send. They now say what happened, that the model must not repeat it, and that only an approver can create or revoke a grant. The user messages say what the approver ran into: `A standing approval with that label already exists.` and `There is no such standing approval to revoke.` Reason codes and retry classes are unchanged, and `docs/formats.md` puts message texts outside the format versioning rule, so no format version changes.
- The model message of `grant_not_allowed` no longer tells the model to request a grant within the limits or approve each call, neither of which it can do. It now says that the model must not repeat the request and that an approver must approve each call or create a grant within the limits.
- `lake build` also builds the `writ` executable, so the binary that `scripts/cli-test.sh` and the `@anijani/writ` differential test run is never stale.
- The shadow model in `WritSpec` adopts the principal ledger an accepted `ledger_sync` brings, taken as is, as spec sections 6 and 7 specify, so the trace checkers judge later steps against the entries and tombstone another session wrote. The theorem 9 checker (`t9Ledger` in `WritSpec/Checks.lean`) judges whether a `ledger_sync` clears the tombstone by the model's tombstone instead of the kernel's state. The mutation set still catches all 56 mutants.
- The trust boundary (spec section 10 and the README) says that the host authenticates the freshness of every approver message that names no request (`grant_create`, `permission_add`, `escalation_ack`): the kernel takes a replayed one for a fresh one, so the host must refuse one replayed from another session or an earlier decision. `corpus/attacks/cross-session-escape.jsonl` pins a replayed `grant_create` the kernel accepts in another session.
- `writ --help` lists `import mcp`, `diff` and `traces`.
- Section 15 of `docs/design.md` moves the Python binding and the SEP-2848 profile from the v0.1 milestone to what main delivers unreleased, with the release workflow; v0.1 is now the first tagged release, which publishes the release binaries, `@anijani/writ` on npm, `writ-kernel` on PyPI and the corpus tarball; the Reservoir listing follows once the repository and the tag are public, and the release version follows section 9's rule (a minor bump, `0.2.0-preview.1` unless the owner decides otherwise), since milestone names are not release versions. Python framework adapters join the v0.2 list. Section 13 says that the profile adds no check for immutable binding, cancel after claim or reservations on execution error, because the kernel already enforces each: SEP-2848's immutable call binding is an approval's binding to the call digest, which holds whatever the policy's `binding` field says.
- `.github/workflows/ci.yml` pins `actions/checkout` and `actions/cache` to full commit SHAs with the tag in a comment, as `release.yml` pins its actions: checkout v7.0.1, the version `release.yml` uses, and cache v6.1.0, both on Node 24 (cache v4 runs on Node 20).

### Schema
- The policy format `"writ": "0.1"` gains optional layer-2 fields: top-level `extends`, `labels` and `rules`, and `labels` on an action (`schema/writ.policy-0.1.schema.json`). The change is additive, so the format version stays `0.1`; a document without these fields is a layer-1 policy, decoded as before.
- The policy format `"writ": "0.1"` gains an optional `source` on each action (`schema/writ.policy-0.1.schema.json`): `tool_digest` is required and must be `"sha256:"` plus 64 lowercase hex digits, `server` and `tool` are strings of at most 512 UTF-8 bytes, `annotations` is an object, and any other key is an error. The change is additive, so the format version stays `0.1` and the next release takes a minor bump.

## 0.1.0-preview.1 (2026-10-22)

The first preview of Writ: the Lean kernel with its proofs of spec section 8's theorems 1 to 12, the `writ` command, the WebAssembly build, the `@anijani/writ` TypeScript package with its AI SDK adapter, and a local browser playground. The release version is `0.1.0-preview.1` for the Lean package, the CLI and `@anijani/writ`, while the kernel version every state records stays `0.1.0`; while it does, a state moves between this preview and 0.1.0 unchanged.

### Frozen formats
From this release, any change to event fields, reason codes or verdict semantics bumps the version of every format it touches and is listed here, and an additive optional field bumps the release's minor version (spec section 9, `docs/formats.md`). Reason codes appear in trace verdicts, in state and as policy `messages` keys, so a new, renamed or removed reason code, or a change to the retry classes, bumps `writ.trace`, `writ.state` and the policy format together:
- `writ.trace/1`, the conformance trace format.
- `writ.state/1`, the stored session state, with `kernel_version` `0.1.0`.
- The policy format `"writ": "0.1"` (`schema/writ.policy-0.1.schema.json`).
- The reason codes and retry classes in `schema/reasons.json`.
- The `writ-call-v1` call digest (vectors in `corpus/digests/call-v1.jsonl`).

### Added
- `scripts/pack-check.sh` builds `packages/writ`, fails unless its tarball holds exactly the compiled `dist/src` code with its declarations and source maps (which embed the TypeScript sources), the kernel, `package.json`, `README.md` and `LICENSE`, then installs the tarball into an empty project, runs the root, `simple`, `ai-sdk` and `firestore` entry points from it and type-checks a TypeScript consumer of all four. `prepublishOnly` runs it, and `npm run build` starts from an empty `dist`.
- `playground/`, a static browser page that runs the WebAssembly kernel on a policy and events you choose: you play the agent, the approver and the tool, see each verdict and the session state, and step through the corpus traces with each step checked against its `expect`. Local only (`node playground/build.mjs && node playground/serve.mjs`).
- `@anijani/writ/ai-sdk`, a Vercel AI SDK adapter: `writTools` wraps every tool's `execute` so it runs only after a claimed `gate.dispatch` with the digest of the input the SDK executes, and gives a `toolApproval` function that proposes each call and never auto-approves, so an edited or replayed message history, or an SDK approval without a Writ approval, runs nothing. Streaming (`async function*`) tools keep streaming, an input that is not plain JSON is denied `invalid_input`, `approve` takes the shown call so a server can rebuild the adapter per request, and a `toolDigests` value that is not a non-empty string or a `cost` value that is not a function throws `WritInputError` when the adapter is built. `examples/ai-sdk` runs it against `ai` 7.0.135.
- `examples/langgraph`, which replays the `langgraph-resume` traces through a real LangGraph.js graph and checks the gate's verdicts against them, and the `langgraph-resume/argument-swap` trace, where a resumed node swaps an approved call's arguments (Loopjacking) and the kernel refuses the swap.
- `@anijani/writ/simple`, an opt-in minimal path: `simpleGate` and `simplePolicy` turn a map of tools to `"none"` or `"per_call"` into a normal layer-1 policy and gate with the user as the only approver. The spec's minimal policy example now names its approver roles and passes `writ check`.
- `docs/sep-2848.md` and `corpus/sep-2848.json` map the corpus to the seven conformance statements of the MCP draft SEP-2848, with one trace per kernel-decidable statement in `corpus/examples/mcp-approval.jsonl`; `WritTests/Sep2848.lean` checks the mapping during `lake build`.
- A WebAssembly build of the kernel (`scripts/build-wasm.sh`, `build/wasm/`), through the new `Writ.Api` JSON entry points (`check`, `digest`, `canonical`, `initial`, `step`, `replay`).
- `scripts/build-wasm.sh` stamps the build with a hash of its sources (`packages/writ/wasm/writ.source`, from `scripts/wasm-source-hash.sh`), and `npm test` in `packages/writ` and `examples/langgraph` refuses to run on a stale build.
- The `@anijani/writ` TypeScript package in `packages/writ`: kernel wrapper, call digests, a gate with `MemoryStore`, `seal` and `open`, the untrusted-report clamp, and `FirestoreStore` at `@anijani/writ/firestore`. Ready to publish to npm as a public scoped package under Apache-2.0, with `LICENSE` in the tarball; `prepublishOnly` refuses a stale WebAssembly build or a failing test.
- `Kernel.tombstone` and `Kernel.inspect` in `@anijani/writ`, with the `SessionView`, `CallView` and `MeterView` types. A kernel error that names its input throws `WritInputError` with the argument's name as `path`.
- `open(sealed, key, expect)` in `@anijani/writ` refuses a sealed state whose `session_id` or `state_version` differs from the server's, and refuses text over `MAX_SEALED_CHARS` before decoding it. `canonicalize` refuses an array with holes or extra properties.
- `corpus/digests/call-v1.jsonl`, test vectors for the `writ-call-v1` call digest.
- `writ check` warnings `meter_without_cap`, `principal_meter_without_window`, `per_call_above_cap` and `retry_without_attempts`, for meters and retries that do less than they seem to.
- `Gate.killPrincipal` and `Gate.clearPrincipalKill` in `@anijani/writ`, which set and clear a principal's tombstone in the stored ledger without a session, through the new `Store.commitLedger`.
- `GateOptions.maxStateBytes`, a byte budget per session (default `store.maxStateBytes`, else `MAX_INPUT_BYTES / 2`, never above the store's own limit; `FirestoreStore.maxStateBytes` is 900000). Growth events are refused above seven eighths of it, so kill, end and reports keep headroom, and a stepped state over the budget is not committed. Both throw the new `WritStateFullError`.
- `GateOptions.retiredPolicyTexts`: a session started under a retired policy can still `end`, `kill`, `result`, `outcomeUnknown`, `reconcile` and `inspect`, so its dispatched calls settle.
- `Gate.inspect(sessionId)`, the stored session's `SessionView` at the gate's clock, for crash recovery.
- `GateResult.reason`, `ProposeResult.requestId` on `needs_approval`, `DispatchResult.claimed` and `ReportResult.overrun`.
- The `@anijani/writ` tarball ships the kernel (`wasm/writ.wasm` and `wasm/writ.mjs`), and its README covers the whole API without the spec. The example imports `@anijani/writ` by name and makes session ids with `randomUUID()`.
- JSON formats for policies, events, verdicts, state (`writ.state/1`) and conformance traces (`writ.trace/1`), a JSON parser and printer with canonical form and the SHA-256 policy digest, and the `writ` command (`check`, `digest`, `replay`, `oracle`, `explain`). See `docs/formats.md`.
- `schema/writ.policy-0.1.schema.json` for editor validation, `schema/examples/assistant.json` as a sample policy for a general-purpose assistant, and `scripts/cli-test.sh` with the cases in `tests/cli/`.
- Executable kernel core: `step : Policy → State → Event → State × Verdict` and `run`, covering sessions and turns, propose, approve and reject with quorum consent, grants, dispatch with retries and outcome reconciliation, meters with session and principal scope, failure escalation, reset, kill and log-only mode.
- `Policy.check` for authoring mistakes, including `empty_consent_group`, and `writ check` warnings `cost_threshold_without_consent` and `messages_not_applied`.
- `Inv.check`, an executable state invariant checked after every step of the test traces.
- Trace checkers for the frame lemma and theorems 1 to 12 against a spec-derived shadow model (`Writ.Checks`), and a seeded trace fuzzer with several live sessions per principal, a shrinker and a mutation set (`writ-fuzz`).
- `writ-fuzz --mutants` prints in how many traces each mutant was caught and fails when any is caught in fewer than 5 (`mutantFloor` in `WritTests/FuzzMain.lean`). The generator makes more approver edits whose escalators raise the consent, approvals from automated approvers on `human_only` consent, grants whose expiry is measured from a `not_before` ahead, and retries of calls a `reset` made Unknown, so every mutant clears that floor.
- The `WritProofs` Lean library, built by `lake build`, proves spec section 8's theorems 1 to 12 over the shipped kernel (consent, grant accounting, permission, at most once, terminal absorption, epoch and freshness, kill, bounds, ledger, default deny, escalation and rejection memory) and its supporting results: the frame lemma, characterization of acceptance for every event kind, witness traces for every reason code, decision, call status and shadow kind, policy check soundness for degenerate limits, origin independence, monotone time and seq, and the well-formedness invariant. `WritProofs/Axioms.lean` pins every theorem's axioms, and the library builds with `warningAsError`, so a `sorry` fails the build.
- `scripts/check-proofs.sh` fails when `WritProofs` uses `sorry`, `admit`, `native_decide`, `unsafe` or `axiom`, when an axiom list pinned in `WritProofs/Axioms.lean` names an axiom other than `propext`, `Classical.choice` and `Quot.sound`, or when a name the README's Proof status section cites as proved has no `#print axioms` line in `WritProofs/Axioms.lean`. The CI workflow (`.github/workflows/ci.yml`) runs it after `lake build` and `scripts/cli-test.sh`, followed by `writ-fuzz --mutants` and `writ-fuzz --traces 1000`, and installs elan from an installer script pinned to a release commit.
- Theorem 9 in `WritProofs` over sessions of several policies and out-of-band tombstone writes: `multi_cap` (each claim within its own policy's cap), `multi_kill` (no claim on a stored tombstone), `multi_window` (policies that agree on a principal meter never prune each other's entries inside its window at the pruning commit's time or later) and `multi_cleared` (a session that saw the tombstone never claims again, even after a clear).
- Origin theorems in `WritProofs` for the records section 8's statements read: `grant_origin` (a grant's limits are those of its `grant_create`), `call_origin` and `generation_recorded` (a call's tool, digests, escalators and generations are those its `propose` and edits carried), and with them `consent_claim_fired` (theorem 1 (b) over the escalators of the `propose` event), `memory_origin` and `rejected_until_user_turn` (theorem 12 over events).
- Origin theorems in `WritProofs` for approvers, the requester and the TTL anchors: `approver_origin` (every attested approver's principal, kind and roles are those of a `session_start` or `approver_attest`), `requester_origin` (the requester is the one every accepted `session_start` carries) and `call_times` (a call's `requestedAt` and `authorizedAt` are the times of the events that requested approval and authorized it), with `approve_fresh_event` and `claim_authorized_ttl_event` (theorem 6's TTLs measured from those event times).
- Report and counter theorems in `WritProofs`: `overrun_commits_actual` and `overrun_verdict` (an accepted report of an actual cost above the reservation commits it in full, the excess dated at the report, is answered `overrun` and counts one failure), `report_commits_actual` (a report at or below the reservation commits exactly the reported cost and decides nothing), and `failure_total_step`, `failure_tool_step` and `escalations_step` (per step, the failure counters and the escalation count change only as section 6's failure rules say, a report that both fails and overruns counting once).
- Ledger, grant and accounting theorems in `WritProofs`: `claim_stored` (a claim stores its ledger with its new entry), `multi_window_ordered` (on one monotone clock no commit prunes an entry a later commit still counts), `multi_kill_after` (no claim after a kill unless a clear follows it), `grant_use_returned` and `grant_released_all` (a call that ends without dispatch returns its grant use), `session_entries_own` and `accounting_session` (the accounting invariant for every session-scope entry) and `report_commits_calls` (a calls meter commits exactly 1).
- `docs/theorems.md`, which maps each theorem of spec section 8 to the Lean statements that discharge it, with what each assumes and what none of them states, and `scripts/print-statements.sh [--defs]`, which prints every pinned statement without its proof (and the `WritProofs` definitions they use) for review without reading the proofs or the kernel.

### Schema
- New JSON formats: policy `writ: "0.1"` (JSON Schema in `schema/writ.policy-0.1.schema.json`), `writ.trace/1` and `writ.state/1`, described in `docs/formats.md`.
- Reason codes, retry classes, decision codes and status codes are versioned schema surface (spec section 6): adding or renaming one is listed here.
- Amount strings are limited to 78 digits; per-action `messages` are shape-checked (keys are reason codes, values `{ model?, user? }`).
- Consent is a list of clause groups, each with a `distinct` flag; a clause is `{ quorum, roles, human_only, exclude_requester }`.
- Each escalator is `{ consent, grantable }` instead of a bare consent.
- `meters` is a list of meter names per action, replacing the single `meter`.
- A meter declares a `unit`, either money in a currency or `calls`, and an optional `cap`.
- Actions accept `approval_ttl_ms` and `authorized_ttl_ms`; `limits` accepts `escalation_scope` (`session` or `tool`).
- `result` and `reconcile` take `outcome` (`succeeded`, `failed` or `declined`).
- `escalation_ack` carries the `escalation` it acknowledges.
- `grant_create` gains `max_cost`.
- New `ledger_sync` event, for several live sessions of one principal sharing a stored ledger.
- `grant_revoke` drops `by` and `approve` drops `display_digest`; these audit fields move to the trace format.
- New reasons `ledger_conflict`, `session_proposal_limit` and `session_approval_budget`.
- Repeated proposals report their current state with the dispositions `existing(status)` and `authorized`.
- `MeterEntry` gains `excess` and `excess_at`.
- Reason `protocol_order` is removed. A call-scoped event that does not fit the call's status is rejected with a reason naming that status.
- New reasons `call_awaiting`, `call_authorized`, `call_dispatched`, `call_unknown` and `not_escalated` (retry class `fix_request`), and `call_ended`, `retry_not_allowed`, `already_reconciled` and `approver_changed` (retry class `never`).
- New decision `overrun` with `meters`, for a `result` or `reconcile` that commits an actual cost above the reservation on some money meter. A release (`no_effect: true`, or outcome `declined`) reports no overrun, whatever `actual_cost` it carries.
- A proposal for a tool the policy does not define is still denied `unknown_tool` but leaves no call record, so its `call_id` stays unused.
- Every string in an event, except in `origin`, `audit` and the `ledger` object of `session_start` and `ledger_sync`, is limited to 512 UTF-8 bytes.
- New `writ check` warnings `meter_without_cap`, `principal_meter_without_window`, `per_call_above_cap` and `retry_without_attempts`.
- The idempotency key is `H(principal, session_id, call_id)`, adding the principal.
- WebAssembly ABI: `writ_call` gains fn 8 `tombstone` (set or clear a ledger's tombstone) and fn 9 `inspect` (a read-only view of a session's calls and meters). Every error envelope names the argument at fault in `input` (`policy`, `state`, `event`, `ledger`, `traces`, `json`, `digest` or `time`), except binding faults (an unknown function, a failed initialization, a bad tombstone flag). `step` and `inspect` refuse a state made under another policy, and `initial` refuses a digest that is not the policy's.
- New contract file `schema/reasons.json`: every reason code with its retry class, in `Reason.all` order. `@anijani/writ` exports it as `REASONS` and `RETRY_CLASSES`.

### Changed
- Every reason's default messages are reviewed. The twelve host-protocol reasons (`not_started`, `already_started`, `stale_seq`, `time_decreasing`, `state_version_mismatch`, `policy_digest_mismatch`, `duplicate_call`, `unknown_approver`, `approver_changed`, `attempt_order`, `idempotency_key_mismatch`, `turn_state`) no longer tell the model to renumber, reload or resend what only the host controls; their model message says the system that runs tool calls hit an internal error and the model must not change or repeat its request. Reason codes and retry classes are unchanged.
- `@anijani/writ` API break: the approver fields of `ApproveInput`, `RejectInput`, `GrantCreateInput`, `PermissionAddInput`, `EscalationAckInput` and `ApproverAttestInput` are renamed `approverId` (the event JSON keeps `approver`).
- `@anijani/writ` API break: gate results are discriminated types. `propose` returns `ProposeResult`, narrowed by `kind` (`allowed`, `needs_approval` with `requestId`, `denied` with `reason` and `status`, `rejected` with `reason`); `dispatch` returns `DispatchResult`; `result` and `reconcile` return `ReportResult`.
- `@anijani/writ` API break: `Store.commitLedger` is required, so custom stores must implement it.
- `@anijani/writ` API break: `defaultIdempotencyKey(principal, sessionId, callId)` replaces `defaultIdempotencyKey(sessionId, callId)`, matching the spec's `H(principal, session_id, call_id)`.
- `@anijani/writ` API break: a stored session under another policy throws `WritPolicyChangedError`, carrying `sessionId` and `policyDigest`, instead of `WritKernelError`.
- `createGate` checks `policyText` and every retired policy text, and throws `WritInputError` on the first that fails `check`.
- `createGate` throws `WritInputError` (path `retiredPolicyTexts[j]`) when a retired policy gives a principal meter another kind (money or calls), currency or `window_ms` than the live policy or an earlier retired policy, since ledger entries carry no unit, so amounts in unlike units would add up in one total, and sessions sharing a principal ledger prune it by their own policy's window.
- Ledger pruning goes by scope: a step prunes the session's meter list only by the policy's session-scope meters and the principal ledger only by its principal-scope meters, so a session meter never prunes the principal ledger, whatever its name, and an entry whose meter the policy defines only in the other scope, or not at all, is never dropped.
- When a binding ends a session after a `ledger_conflict` while handling a `result` or `reconcile`, it resends the report as `reconcile` on the ended session and returns that verdict, so the call settles in one call. `@anijani/writ` does this, for example when the principal's tombstone was cleared, and applies the same untrusted clamp to the resent report; an `outcomeUnknown` is not resent. Once a session has ended, by the gate or by `end`, `@anijani/writ` also resends a `result` rejected `session_ended` as `reconcile`, so the session's other dispatched calls settle through `result`; a report is resent at most once.
- `ledger_sync` on an ended session is accepted when it clears a set principal tombstone (a live session still gets `ledger_conflict`), so after the tombstone is cleared the session's dispatched and Unknown calls can still settle with `reconcile`.
- `DispatchInput.attempt` is optional and defaults to the stored call's attempts plus one, read once per `dispatch` call.
- TTLs are half-open: a call is valid strictly before its deadline.
- Meters commit the actual cost; an overrun records its excess as a separate amount dated at the report.
- Unknown and unexposed tools are never shadowed, so theorem 10 (default deny) holds under every mode, including log-only.
- Propose checks run in a stated order (spec section 6, Propose), and the first that fails gives the denial reason.
- A `session_start` whose `session_id` already owns entries in the ledger it brings is rejected `already_started`.
- `ledger_sync` refuses (`ledger_conflict`) a stored ledger that holds one of the session's own entries more often than the session does, so a retry can no longer take a meter over its cap through a duplicated reservation.
- Spec wording in `docs/design.md` matched to the proved statements after the section 8 review: theorem 1 (a) and section 6 (Approve) count an approver's edit by the digest and cost it set; theorem 8 and section 6 (Meters) add a `ledger_sync` or `session_start` that brings in a principal ledger above the cap to the ways usage can exceed it; theorem 9's cross-session claims assume one trusted monotone clock that stamps every commit attempt, and section 6 (Meters) says an entry dated after a session's last event was written meanwhile by another session instead of by one whose clock runs ahead; section 6 says the rejection check at dispatch applies to first attempts only, that a report both failed and overrun counts once, and how the escalation count rises; the goals and the supporting results say the characterization lemmas rule out a kernel safe by refusing everything only together with the witness traces; the supporting results say the witness traces are under a witness policy and checked by `decide +kernel`, that the policy check refuses an unexposed action whose own mode is `log_only`, that origin independence is per step, that the invariant holds on every reachable state and that no theorem being vacuous is an aim; and the proof architecture says which theorems are stated over traces.
- The spec-side model and fuzz judge (`Inv.check`, the shadow model and the trace checkers) move from `Writ/Spec` in the kernel library to their own library `WritSpec`, and the fuzz driver from `FuzzMain.lean` to `WritTests/FuzzMain.lean`; namespaces and identifiers are unchanged.
- The WebAssembly build inputs move from `wasm/` to `build/wasm/`; the build output in `packages/writ/wasm/` keeps its place. The source stamp hashes file paths, so `packages/writ/wasm/writ.source` changes.
